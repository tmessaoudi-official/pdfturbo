### The one finding to fix first — ✅ FIXED 2026-06-23

**Redaction burn is misplaced on a *cropped* page → the secret can leak** (P1, but data-safety — treat as near-P0). A cross-domain catch: the redaction agent confirmed the burn is solid in isolation, but the export-pipeline agent found the **crop + redaction** combination is never reconciled — the raster burn rects do not subtract the crop origin, so on a cropped+redacted page the black box lands in the wrong place and the underlying text is exposed in the export. ## P1 — high-impact (fix this sprint)

### P1-1. DOCX editor modal has no focus trap, no Esc-to-close, no backdrop dismiss

- **Domain / category:** DOCX editor (read/edit/toolbar/find-replace/tables/paste-from-Word) + DOCX→PDF export — `a11y`
- **Location:** `src/docx/docxEditorController.ts` 81-86, 184-187
- **Evidence:** The modal sets role="dialog" + aria-modal="true" but the only close affordance is the ✕ button. No Escape keydown handler on the modal, no focus trap keeping Tab inside the dialog, no backdrop click-to-close. CLAUDE.md states every modal needs its own Esc branch and the bates/signers panels each ship focus-trap/Esc/backdrop; this one ships none. A keyboard/AT user can Tab into the inert app behind it and cannot dismiss with Esc (the find/replace bar's Esc only closes the bar).
- **Fix:** Add an Escape keydown handler on modal calling close(), a focus trap (reuse src/utils/focusTrap.ts), initial focus on open, and focus restoration on close.
- **Verify:** isReal=True (high) — Re-read docxEditorController.ts directly. Lines 81-86 build a div role="dialog" aria-modal="true" overlay; modals.css confirms it is a full-viewport position:fixed inset:0 z-index:9500 backdrop (rgba(0,0,0,0.45)) covering the inert app. Verified every claimed absence: (1) No Esc handler — grep found NO document-level keydown in src/docx; the app's central Esc chain (src/ui/binders/keyboardBinder.ts:21-43) has explicit branches for every PDF modal (signature/watermark/bates/compress/sign/signers/textOptions/ocr) but NONE for the docx editor, because the controller is self-contained and not part of app.ui. (2) No focus trap — both batesPanel.ts:4,56 and signersPanel.ts:5,74 import and call trapFocus from src/utils/focusTrap.ts; docxEditorController imports/uses neither. (3) No backdrop dismiss — no mousedown/outside-click/contains() handler in the controller. (4) No initial focus or focus restoration — no .focus()/activeElement in the file. The sole close affordance is the ✕ button (lines 107-111 wired at 182 → close() at 184-187). The finding's parenthetical is also correct: findReplaceBar.ts:119-122,129-132 Esc calls close() on the BAR, not the modal. CLAUDE.md documents many docx ceilings (tables, run formatting, PDF-export scope) but NONE about modal a11y; no KNOWN_ISSUES entry — so this is not a documented intentional ceiling. The finding is genuine and matches the established codebase convention that every modal ships its own Esc/focus-trap (bates/signers panels do).

### P1-2. Redaction (and overlay-text) burn is misplaced on a cropped page — secret can leak

- **Domain / category:** Export pipeline + positioning — `data-safety`
- **Location:** `src/export/exportPipeline.ts` 286-313, 316-339 (burn) vs 220-222 (crop applied) + 269-270/349-350 (canvas sized from cropped box)
- **Evidence:** rasterizePageWithRedactions -> buildPageOverlays calls page.setCropBox(effBox...) on tempPage when docPage.crop is set, so pdf.js renders only the cropped sub-region into `offscreen` (sized from cropBoxR, the cropped box). But the redaction burn uses raw full-page coords with no crop-origin offset: ctx.fillRect(Math.round(el.x*SCALE), Math.round(el.y*SCALE), ...). el.x/el.y are relative to the full un-cropped page top-left, while the canvas origin is now the crop window top-left, so the burn is offset by (cropOriginX,cropOriginY)*SCALE. The overlay TextElement canvas draw (te.x*SCALE) has the same defect. The vector renderRedaction path IS crop-correct (tp() adds cropOriginX/Y) but redaction-bearing pages always route to the raster path, so the broken path is the one that runs. No test combines crop + redaction (blockers-redaction only varies rotation).
- **Fix:** In the redaction and text canvas loops, subtract the crop origin in display space before scaling — map docPage.crop to display space (contentRectToDisplay) and use (el.x - cropDisplayX)*SCALE. Add a crop+redaction browser test (red secret under a crop window) mirroring blockers-redaction.
- **Verify:** isReal=True (high) — Verified end to end in the code. (1) exportService.ts:591,610-613 — redaction-bearing pages always route to rasterizePageWithRedactions; the crop-correct vector renderRedaction (which adds cropOriginX/Y via tp()) never runs for redactions. (2) exportPipeline.ts:220-222 — buildPageOverlays calls page.setCropBox(effBox) unconditionally when docPage.crop is set, and the rasterizer invokes buildPageOverlays at line 254, so tempPage gets the cropped CropBox. (3) exportPipeline.ts:269-282 — cropBoxR = getPageCropBox(tempPage) reads back effBox and the canvas is sized from it; pdf.js renders honoring the CropBox, so canvas (0,0) = crop-window top-left. (4) exportPipeline.ts:305-310 (redaction) and 324/336 (overlay text background+glyph) burn at ctx.fillRect/ fillText(el.x*SCALE, el.y*SCALE, …) with NO crop-origin term. el.x/el.y stay relative to the source content-box top-left — confirmed by pageService.cropPage (144-193), which only stores page.crop via SetPageCropCmd and never re-bases element coordinates. Net: the burn is offset by (crop.x, crop.y)*SCALE on any user-cropped page, so a redaction rectangle (and overlay text) lands in the wrong place — it can fail to cover the content it was meant to hide, a genuine redaction-leak correctness/security defect. Not a documented ceiling: CLAUDE.md #G23 explicitly claims the redaction rasterizer 'inherit[s] the crop (they re-read getPageCropBox)', but re-reading the cropbox only sizes/clips the render — it does not re-base the canvas burn coords, so the doc asserts a correctness the code does not implement. No test guards it: crop-tool.browser.test.ts exercises crop+rotation+clipped-pixels but never crop+redaction; blockers redaction tests vary rotation only; nothing combines crop with a redaction/text burn. The fix in the recommendation (subtract the crop origin mapped to display space before scaling, plus a crop+redaction browser test) is correct. P1 rather than P0: it manifests only at the crop+redaction intersection (behind VITE_FEATURE_CROP, requires the user to have cropped) and misplaces rather than guaranteeing full exposure, but a redaction leak is a security-relevant correctness bug.

### P1-3. Structural table edits are silently discarded on save with no user feedback

- **Domain / category:** DOCX editor (read/edit/toolbar/find-replace/tables/paste-from-Word) + DOCX→PDF export — `data-safety`
- **Location:** `src/docx/docModel.ts` 373-382
- **Evidence:** tableEditing() is enabled in the schema (docxProseMirror.ts:21, docxSchema.ts:13-23) and tables are full editable PM nodes, so a user can delete a table/row via base-keymap Backspace. On save, reconcileContainer does `if (domTables.length !== modelTables.length)` and silently routes to reconcileParagraphsOnly(blocks.filter(paragraph)), which leaves the ORIGINAL DOM tables verbatim. A table the user deleted in the editor is still present in the downloaded file, with no notify()/toast. The saved document silently diverges from what the user sees.
- **Fix:** Either make table structure genuinely read-only via a transaction-filter plugin, or detect the divergence in save() and surface notify('docxEditor.tableStructureUnsupported','warn') so the dropped structural edit is visible.
- **Verify:** isReal=True (high) — Re-read all cited code. Confirmed the full chain: (1) docxSchema.ts:12-23 adds prosemirror-tables `tableNodes` as full editable block nodes; docxProseMirror.ts:255 enables `tableEditing()` and line 277 installs `baseKeymap` — Backspace/Delete are generic node/range deletion commands, and there is NO transaction-filter plugin gating structural changes, so a user CAN delete a table or row via the keyboard (a NodeSelection on the table + Delete, or a cross-table range delete). (2) On save, docxProseMirror.ts:321 calls docToDocModel → applyBlocks → reconcileContainer (docModel.ts:373). At line 379 `if (domTables.length !== modelTables.length)` it routes to reconcileParagraphsOnly, which (docModel.ts:428-431) only touches `w:p` children — the original `w:tbl` elements pass through the XMLSerializer verbatim. So a table the user deleted in the editor is still present in the downloaded file. (3) docxEditorController.ts:154-162 `onSave` unconditionally fires notify('docxEditor.saved','info') on success; grep confirms no `tableStructureUnsupported` key and no divergence detection anywhere in src/docx/. The saved document silently diverges from what the user sees, with no toast.

This is NOT a documented intentional ceiling. CLAUDE.md and the spike verdict describe Slice 3a tables as "structure read-only" but enforce that only at the TOOLBAR level: tests/browser/docx-tables.browser.test.ts:171-198 asserts only that add/delete-row/column/merge/split toolbar buttons are absent — it does not block or test the keyboard deletion path. The intended ceiling is "no add/merge/split affordance"; accidental structural DELETION via the generic keymap is an ungated gap that produces a silent save/display divergence.

Severity: P1 is defensible — silent data-integrity divergence (saved file ≠ on-screen content) with zero feedback. The mitigating factors (flag-gated VITE_FEATURE_DOCX_EDIT beta, requires a specific keyboard interaction, file is not corrupted — it just retains the deleted table) make a P2 argument reasonable, but the silent, invisible nature of the divergence keeps it at P1.

### P1-4. Form fills are not undoable (mutation bypasses the Command/history system)

- **Domain / category:** Forms fill / flatten (#62) + AcroForm residue — `undo`
- **Location:** `src/core/pdfTurboApp.ts` 169-171
- **Evidence:** setFormValue() mutates _formValues directly (`this._formValues[sourcePdfId][fieldName] = value`) and pageRenderPipeline.ts:150-153 calls it + autosave() with no historyManager.push anywhere in the form-fill path. CLAUDE.md's cardinal rule: every mutation must go through a Command pushed to historyManager or undo breaks. Form-fill is not listed as a documented non-undoable exception.
- **Fix:** Route form-value changes through a SetFormValueCmd capturing {srcId, fieldName, oldValue, newValue} pushed to historyManager, mirroring text/element edits. Debounce text-field input events into one command on blur so each keystroke isn't a separate undo step.
- **Verify:** isReal=True (high) — Verified the cited code directly. pdfTurboApp.ts:169-171 — setFormValue() does `this._formValues[sourcePdfId][fieldName] = value`, a direct mutation. pageRenderPipeline.ts:148-153 — the formFieldOverlay.render callback invokes setFormValue() + autosave() only. grep across src/ for formValues/setFormValue and for command classes confirms NO SetFormValueCmd exists in src/core/commands/ and NO historyManager.push/record/execute is reachable from the form-fill path. By contrast, overlay text edits DO route through undoRedoController.handleTextInput → historyManager.record(new TextEditCmd(...)), confirming the asymmetry: overlay text is undoable, AcroForm field fills are not. Checked CLAUDE.md, KNOWN_ISSUES.md, and docs/reviews/: the forms section documents only flattening (#62) and field-type support limits; the only adjacent note (CORE-5) is about undo HISTORY not surviving reload — a distinct concern. Form-fill undoability is NOT listed as an intentional ceiling/exception anywhere, so the project's own cardinal rule ('every mutation goes through a Command pushed to historyManager') is violated. Severity calibration: kept at P1. It is a genuine missing-undo gap on a primary editing surface, breaking a stated invariant, and the fix is non-trivial (needs debounce/coalescing per the recommendation). The finding's secondary claim that undo 'silently jumps over' form edits to pop a prior element command is partly speculative — form fields are live overlay inputs whose DOM value isn't disturbed by Ctrl+Z, so the practical symptom is 'form fills simply have no undo', not a confusing cross-element revert. That nuance does not change the core verdict.

## Per-domain health summaries

### Text overlay + addText tool + rich-text toolbar (Slice 1 + Slice 2)  (8 findings)

This domain is largely healthy: all 13 controls round-trip cleanly through toJSON/fromJSON (conditional spread + typed guards, no schema bump needed), every mutation goes through a MoveResizeCmd so undo is sound, clamps are NaN-safe (Number.isFinite, no parseFloat||x), and the format painter is disarmed on document load so it cannot leak across PDFs. The real defects are: (1) the raster export path (used on redaction-bearing pages) silently drops all Slice-2 advanced attrs AND alignment AND underline/strike — an undocumented divergence from the vector bake, not the "pixel fidelity uncertain" caveat the docs imply; (2) a corrupted recentColors localStorage value crashes the swatch-row render at startup (no Array.isArray guard before a spread); (3) missing UX feedback for the format painter and clear-formatting. No P0, no data-loss (undo covers everything), no security issues found.

### True-edit engine (src/utils/contentStreamEditor.ts + src/handlers/textEditHandler.ts)  (5 findings)

The true-edit engine is mature and heavily hardened against the exact data-loss vector this review targets. No path blanks bytes before a replacement is guaranteed: Path 3 (F9) builds the redraw inside a try{} before blankShowOp, and every refuse gate (Type3, invisible Tr 3/7, vertical, XObject, Arabic, non-WinAnsi, rotated/sheared/mirror CTM) returns false before any mutation. The overlay-fallback toast is surfaced on every refuse, undo funnels through a single ReplaceSourcePdfBytesCmd with a TOCTOU snapshot guard, and en/fr/ar locale keys are parity-clean. Found no P0/P1 issues; the few defects are minor edge cases.

### Export pipeline + positioning  (4 findings)

The export pipeline is mature and well-factored: coordinate flips are centralized in transformPoint/tp(), FS-Access transient-activation ordering is correct in every byte-export path, byte-identical-when-off guarantees hold, Bates full-document numbering is correct, and en/fr/ar toast keys are at parity. The notable genuine defect is that the redaction (and overlay-text) raster burn does not subtract the crop origin, so on a cropped+redacted page the burn is misplaced and the secret can leak — and no test combines crop with redaction. Secondary issues: watermark/Bates draw in raw user space so they orient/anchor wrong on a /Rotate'd page, and two pdf.js render docs are never destroyed (worker leak).

### Shapes / highlight / redaction / comment / ink elements + eraser  (7 findings)

Redaction is genuinely destructive on every PDF byte-export path: any page with a redaction element is routed through rasterizePageWithRedactions, which flattens the page to a PNG and discards the source content stream (no extractable text leak). The historic rotated-page leak (CORE-P0-1) is fixed and pixel-guarded in real Chrome for 0/90/180/270° plus element-own-rotation (G2), and flow export (DOCX/MD/TXT) drops redacted source text. Undo/redo coverage is complete — all shape/highlight/redaction/ink/eraser mutations go through Command objects. The domain is largely healthy; the notable gaps are a data-at-rest concern (unredacted source bytes persist plaintext in IndexedDB), an eraser bbox imprecision, and a UX split between two disjoint erase mechanisms. No P0/P1 found.

### Signatures  (4 findings)

The signing domain is healthy and matches its documented design. Every data-safety and trust invariant the review targeted holds: the .p12 is zeroed in a finally (signingHandler.sign:253 + scrubP12Material), re-signing is refused via ALREADY_SIGNED (preflight runs BEFORE cert generation so no orphan .p12 download), the panel-vs-plain caption leak is guarded in all three entry points (toolBinder, keyboardBinder, pad-cancel), and the experimental incrementalSigner/multiSign/cmsVerify modules are genuinely unwired (zero non-test imports in src/) with the ALREADY_SIGNED guard intact. Locale parity is clean (11 sign.error codes in en/fr/ar) and captions render via textContent. No P0/P1 found; the four minor findings are correctness edges (first-hex /Contents match, field-name collision, appearance band math, PNG-only drawn-signature coupling).

The OCR domain is in good health — no P0/P1 findings. ## Cross-cutting themes

1. **Raster export path is a second-class citizen.** The redaction/thumbnail raster bake (`exportPipeline.ts`) silently drops Slice-2 text attrs, alignment, decorations, and mis-anchors watermark/Bates on rotated pages, and mis-places the redaction burn on cropped pages. The vector bake is correct and pixel-guarded; the raster path is only code-reviewed. Every "feature × redaction/crop/rotation" combination deserves a real-Chrome pixel test.
2. **Silent failures / missing feedback.** Multiple paths "succeed" while dropping work: per-element bake failures, small-widget form fills, structural DOCX table edits, image-decode aborts, format-painter arming. A consistent toast/telemetry convention would surface these.
3. **Data-at-rest.** The unredacted source PDF (plus form/signature data) persists in cleartext in IndexedDB until manual reset — consistent with the local-only design, but the privacy notice should name the shared-machine risk, and a "burn redactions now" option would let the cautious user purge the original.
4. **Modal a11y.** The DOCX editor and restore dialogs declare `role=dialog`/`aria-modal` but lack focus traps and Esc handlers (the panel modals — Bates/watermark/compress — do have them).
5. **URL-scheme hygiene.** Pasted/extracted hyperlink URLs (MD export, Word paste, PDF Link annotations) are not scheme-validated against `javascript:`/`data:` in several spots.
