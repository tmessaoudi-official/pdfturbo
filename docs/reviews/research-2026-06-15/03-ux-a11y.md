## Text-tool defect — root cause

The app has **two distinct text modes that coexist**, and the bug is the interaction between them:

- `addText` mode — the classic "Add Text" tool. Already supports **draw-to-place** (drag a box) via `drawingHandler.handlePointerDown` (`src/handlers/drawingHandler.ts:58` includes `addText` in the placement set) → `handlePointerUp` (`drawingHandler.ts:239-247`) → `app._commitPlacement('addText', x, y, w, h)` → `placementManager.commitPlacement` (`src/ui/placementManager.ts:103-133`). It sizes the box to the drag rect, focuses the input, **then `setMode('select')` + `selectElement`** (lines 128-129). This is the correct, consistent pattern.
- `editText` mode — the unified ISSUE-5 mode. Routed entirely through `canvasClickRouter.handleCanvasClick` (`src/core/canvasClickRouter.ts:42-43`) → `app.handleTextEditClick` (`pdfTurboApp.ts:475`) → `TextEditHandler.handleCanvasClick` (`src/handlers/textEditHandler.ts:57`). It is a **click-only** handler — no pointer-down/move/up, so no drag, no draw-to-place.

### Symptom 1 — "Edit text on blank drops a fixed box, can't draw to place it"
Call path: in `editText` mode, a blank-canvas click finds no text item (`textEditHandler.ts:84-98` hit-test loop, `best` stays null) → `if (!best) { app.addTextAtPosition(e); return; }` (`textEditHandler.ts:103-106`). `addTextAtPosition` (`placementManager.ts:202-229`) creates a `TextElement` at **fixed default size** centered on the click (`textElement.x -= width/2`, line 210-211) — there is no drag geometry because the click handler never saw a pointer-down→up gesture. **Root cause: `editText` is wired as a click handler and reuses `addTextAtPosition` (fixed-size drop), bypassing the drag-to-size path that `addText` already has in `drawingHandler`.** [Verified: read both call paths in full.]

### Symptom 2 — "Add a box then try to move/resize/rotate/delete — it keeps adding/displacing text"
Call path / root cause is in **mode pointer-events gating**:
- `toolModeManager.setMode` (`src/core/toolModeManager.ts:43`) sets `setElementPointerEvents(mode === 'select' ? 'auto' : 'none')`. **In `editText` mode, all element DOM nodes get `pointer-events: none`** — so a placed text box cannot be clicked, dragged, resized, or rotated; the interaction handles (`InteractionHandler`, `src/handlers/interactionHandler.ts`) never receive the pointer-down because the element layer is non-interactive.
- Worse, every subsequent click on the canvas while still in `editText` re-enters `handleTextEditClick`. If it lands on a blank area (or on the box you just placed, which doesn't register as PDF source text), it **drops yet another text box** via `addTextAtPosition` (`textEditHandler.ts:103-106`). That is the "keeps adding text" behavior.
- Note the asymmetry: `addTextAtPosition` (the blank-click drop, `placementManager.ts:223`) **does NOT call `setMode('select')`** — it stays in `editText`. Contrast `commitPlacement` for `addText` (`placementManager.ts:128`) and the `_emitOverlay` path (`textEditHandler.ts:299`) which both **do** switch to `select`. So a true-edit / overlay edit exits to select correctly, but the **blank-click box-drop traps the user in `editText`**, where elements are pointer-events:none → the box is unselectable and every further click spawns another box. **This is the core of symptom 2.** [Verified: `setMode` gating at `toolModeManager.ts:43`; missing `setMode('select')` in `addTextAtPosition`.]

### SEPARATE-modes fix (recommended) — ranked steps
The cleanest fix matches the prompt's recommendation and reuses existing infrastructure:

1. **[P0, SYSTEMIC] `editText` = click-existing-text ONLY.** In `textEditHandler.ts:103-106`, drop the `addTextAtPosition` fallback. A blank-canvas click in `editText` should do nothing (or show the `editText` hint), not create a box. This kills the "keeps adding text" loop at its source. [Verified: that 4-line block is the only place editText creates a box.]
2. **[P0, SYSTEMIC] "Add Text" = draw-to-place, already works — just route the toolbar/`T` button to `addText`, not `editText`.** `addText` already has full drag-to-size (`drawingHandler.ts:58,239-247` → `commitPlacement`) and auto-switches to `select`. Verify the primary "Text" toolbar button (`textModeBtn`/`addTextBtn`, `uiController.ts:354,361`) and the `T` shortcut (`keyboardBinder.ts:40-41`, already → `addText`) point at `addText`. The `editText` button (`✎ Edit Text`, `uiController.ts:354`; `X` shortcut, `keyboardBinder.ts:72-73`) stays as the existing-text editor.
3. **[P1, SYSTEMIC] Auto-switch to Select after placing/editing in every text path.** `addText`/overlay paths already do; ensure `editText`'s true-edit commit (`_openTrueEditInput.commit`, `textEditHandler.ts:430-508`) also calls `setMode('select')` after `_applySourcePdfEdit` so the user lands in a state where they can immediately move/delete the result. (Currently only the `_emitOverlay` fallback switches.)
4. **[P2, PAGE] Add a single-click affordance to `editText`** (e.g. hover cursor / highlight over editable words) so users learn it edits existing text, not place new — see Discoverability.

This fix requires **no new drag code** — `addText` draw-to-place is already implemented and battle-tested in `drawingHandler`. The change is mostly *removing* the editText blank-drop fallback and re-pointing the primary Text button. [Inferred: based on confirmed existing `addText` drag path; low implementation risk.]

## add→select→transform→delete loop (per element type)

| Element | Place via | Drag-to-size? | Auto → `select` after place? | Selectable/transform in its own mode? | Notes |
|---|---|---|---|---|---|
| **Text (addText)** | `commitPlacement` (`placementManager.ts:108-133`) | **Yes** (`drawingHandler.ts:239`) | **Yes** (`:128`) | n/a (switches to select) | Correct, consistent. |
| **Text (editText, blank click)** | `addTextAtPosition` (`placementManager.ts:202`) | **No** (fixed box) | **No** — stays `editText` (`:223`, no setMode) | **No** — elements pointer-events:none (`toolModeManager.ts:43`) | **BROKEN loop** — the live defect. |
| **Image** | `commitPlacement` (`placementManager.ts:135-150`) or `addImageAtPosition` (`:87-101`) | Yes / click | **Yes** (`:148`, `:98`) | n/a | Consistent. |
| **Signature** | `commitPlacement` (`placementManager.ts:182-198`) | Yes | **Yes** (`:196`) | n/a | Consistent. |
| **Shape (rect/ellipse/arrow)** | `drawingHandler.handlePointerUp` (`:177-195`) | Yes | **Yes** (`:260`) | n/a | Consistent. |
| **Highlight** | `drawingHandler` (`:197-210`) | Yes | **Yes** (`:208`) | n/a | Consistent. |
| **Redaction** | `drawingHandler` (`:224-237`) | Yes | **Yes** (`:235`) | n/a | Consistent. |
| **Freehand/ink** | `drawingHandler` (`:212-222`) | Yes | **No** — stays in tool, `selectedElement=null` (`:256-258`) | n/a | Intentional (multi-stroke); deliberate exception. |
| **Comment** | `commitPlacement` (`placementManager.ts:152-160`) | Yes | **Yes** (`:158`) | n/a | Consistent. |
| **Code/QR** | `commitPlacement` (`placementManager.ts:162-180`) | Yes | **Yes** (`:178`) | n/a | Consistent. |

**Finding [P0, SYSTEMIC]:** Every element type auto-switches to `select` after placement **except** (a) freehand (intentional) and (b) **the editText blank-click text drop (the bug)**. Once in `select`, transform + delete are uniform: `InteractionHandler` handles drag/resize/rotate (`interactionHandler.ts:55-75`), Delete/Backspace removes the selected element (`keyboardBinder.ts:32-39`). The loop is *only* broken for the unified-editText blank-drop path.

## Discoverability / labels

- **[P2, PAGE] Dual "Text" tools are confusing (ISSUE-5 root).** Two buttons: `addText` labelled `"T Text"` / title `"Add Text (T)"` (`locales/en.json:15-16`) and `editText` labelled `"✎ Edit Text"` / title `"Edit PDF text — click a word to overlay and edit it"` (`en.json:40-41`, rendered with `'✎ ' + t('toolbar.editTextLabel')` at `uiController.ts:354`). They are presented via a `textModeBtn` split control (`uiController.ts:361`, `.text-split-btn` in `index.html:209`). The two modes behaving differently (draw vs click-drop) with similar names is the discoverability defect — the SEPARATE-modes fix above also clarifies labels: "Add Text" (draw) vs "Edit Text" (click a word).
- **[P3] All tool buttons are i18n'd** through `t()` (labels at `uiController.ts:354-381`; titles in locale `toolbar.*Title` keys). No hardcoded user-visible tool strings found. [Verified: grep over uiController + locales.]
- **[P2] editText hint already tells the user "click on any word"** (`toast.modeHint.editText`, `en.json:299`), but there is no in-canvas cursor/hover affordance signalling which words are editable — discoverability relies on the toast only.

## Keyboard / focus

- **[OK] Esc** is comprehensive: closes settings/help/signature/watermark/code modals and find-bar in priority order, else `setMode('select')` + deselect + blur (`keyboardBinder.ts:6-17`). The inline true-edit input handles Esc locally to cancel (`textEditHandler.ts:515-517`) and `stopPropagation` (`:511`) so it doesn't bubble to the global handler. **[P2]** the inline true-edit input lives on `document.body` (`textEditHandler.ts:521`), not inside a focus-trapped container — acceptable for a single transient input but note it for completeness.
- **[OK] Delete / Backspace** removes the selected element and clears formatting toolbar (`keyboardBinder.ts:32-39`). Guarded behind `if (app.selectedElement)`.
- **[P3] Single-letter tool shortcuts fire without a modifier** (`keyboardBinder.ts:31-101`: t/s/i/a/r/c/b/d/f/h/n/e/x/k/q/w). They are correctly suppressed when focus is in `input, textarea, select` (`:18`). `X` toggles `editText` (`:72-73`); after the SEPARATE-modes fix, confirm `T` (→ `addText`, `:40-41`) remains the "draw a text box" shortcut. [Verified.]
- **[OK] Arrow-key nudge** of selected element with Shift = 10px step (`keyboardBinder.ts:85-100`), including shape endpoints/points.
- **[P2] Inline true-edit input** reflects detected font props into the formatting toolbar and re-enables those controls (`textEditHandler.ts:382-391`), resetting them on close (`:411-420`) — good, but the `aria-label` is the only accessible name (`:342`, `canvas.trueEditInput`), and the editor is not announced as a dialog/region.

## Mobile / touch

- **[OK, MOBILE] Touch targets meet ~44px guidance on mobile breakpoint:** `index.html:346-347` sets toolbar buttons to `min-width:40px; min-height:40px`, `.btn { min-height:40px }` (`:354`), color swatch `36px` (`:356`). Desktop buttons are smaller (`.toolbar-group .btn { height:28px }`, `:167-168`; `.btn-sm`/`min-width:28px` at `:162`). 40px is slightly under the 44px iOS HIG ideal but within the 40px Material minimum. **[P2, MOBILE]** consider bumping mobile toolbar buttons to 44px.
- **[OK, MOBILE] Touch drag-to-edit coexistence** is handled: `interactionHandler.handlePointerDown` (`:61-71`) defers drag start on touch over an input until a 5px movement threshold (`_DRAG_THRESHOLD`, `:31`; `_commitTouchDrag`, `:77-89`) so tap-to-edit still works on touch. This is good — but it only applies in `select` mode (elements are pointer-events:none in `editText`), reinforcing the symptom-2 finding.
- **[P3, MOBILE] The `editText` blank-drop has no drag path on touch either** — same root cause; the SEPARATE-modes fix resolves mobile too, since `addText` draw-to-place already works under pointer events.

## Summary of P0/P1 (actionable)

1. **[P0, SYSTEMIC]** `editText` blank-click drops a fixed unselectable box and traps the user in a non-interactive mode → "keeps adding text" + "can't move/resize/delete". Root: `textEditHandler.ts:103-106` (blank-drop fallback) + `toolModeManager.ts:43` (pointer-events:none in non-select) + `addTextAtPosition` never calling `setMode('select')` (`placementManager.ts:223`).
2. **[P0, SYSTEMIC]** Fix = SEPARATE the modes: `editText` edits existing text only (remove the blank-drop fallback); "Add Text" = `addText`, which already does draw-to-place via `drawingHandler` and auto-switches to `select`. No new drag code needed.
3. **[P1, SYSTEMIC]** Make every text-commit path end in `setMode('select')` (the true-edit commit currently doesn't).
