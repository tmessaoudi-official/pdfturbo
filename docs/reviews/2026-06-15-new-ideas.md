# PDFturbo — New Capabilities / Tools / Mechanisms (research, pre-commitment) 2026-06-15

User ask: think about genuine NEW ideas/tools/mechanisms to integrate — research + test before any
commitment. This doc proposes; nothing is built yet. Each item: what · mechanism/library · client-side
feasibility · builds-on · ROI · spike-to-validate. Constraint anchors: **100% client-side, nothing
uploaded** (the product's whole premise) and **GRDF data policy** (no sensitive data to *external* AI).

> **Key unlock — local AI is policy-compatible.** `transformers.js` (`@huggingface/transformers`) runs
> ONNX models entirely in the browser (WASM, or WebGPU-accelerated), offline after model download
> [Verified: HF docs + v3 WebGPU blog]. Because inference never leaves the device, local-AI features do
> NOT transmit document data anywhere → they are compatible with GRDF's "no data to external AI" rule by
> construction. This turns "AI features" from forbidden into feasible. (Cost: model download MBs + WebGPU
> availability — must feature-detect and degrade gracefully.)

## Tier 1 — high ROI, fits the ethos, builds on what exists

### 1. Searchable-PDF OCR layer (invisible text over scans) — **strongest**
- **What:** today OCR (`src/ocr/*`, tesseract@7) inserts visible `TextElement`s. Add a mode that instead
  lays the recognized words as an **invisible** text layer (PDF text render mode 3, `3 Tr`) precisely over
  the scanned image. Result: a scanned PDF becomes selectable / searchable / screen-reader-accessible with
  **zero visible change** — the canonical "OCR a scan" deliverable every PDF tool ships.
- **Mechanism:** we already get per-word bboxes from tesseract (`flattenBlockWords`); pdf-lib draws text at
  those coords with render mode 3 + a zero-alpha or `Tr 3` invisible font. The contentStream/text-op
  knowledge from the true-edit engine applies directly.
- **Builds on:** OCR engine (done), contentStreamEditor text-op emission, MacroCmd undo.
- **ROI:** very high — it's the #1 expected OCR outcome and we already have the recognition half.
- **Spike:** emit `BT 3 Tr /F .. Tf <pos> Td (word) Tj ET` per word over an image page; verify a PDF reader
  selects the invisible text at the right place. Effort M.

### 2. Sanitize / metadata-scrub tool — **fits privacy ethos perfectly**
- **What:** one-click "clean this PDF": strip XMP + `/Info` metadata (author, producer, timestamps), remove
  embedded JavaScript (`/OpenAction`, `/AA`), file attachments (`/EmbeddedFiles`), and optionally hidden
  optional-content groups (OCG layers). Plus a redaction-completeness check (warn if text still extractable
  under a redaction rect).
- **Mechanism:** pdf-lib catalog/Info manipulation; we already parse content for redaction. No new dep.
- **ROI:** high for a privacy-first, offline tool — "nothing uploaded" + "nothing leaked in metadata" is a
  coherent story, and matters in the GRDF regulated context.
- **Spike:** load a PDF with `/Info` + an `/OpenAction` JS, scrub, re-open, assert both gone. Effort S-M.

### 3. File System Access API — open/save-in-place + recent files
- **What:** open a PDF and **save back over the original file** (no "downloads/ duplicate" churn), plus a
  recent-files list. Modern desktop-app feel.
- **Mechanism:** `showOpenFilePicker`/`showSaveFilePicker`/`FileSystemFileHandle`.
- **Caveat [Verified]:** Chromium-only (Chrome/Edge/Opera 86+); **Firefox/Safari + all mobile lack it** —
  must `if ('showSaveFilePicker' in window)` feature-detect and fall back to the current download path.
- **ROI:** high daily-use UX on desktop Chromium (the dev's own browser); graceful elsewhere. Effort S.

## Tier 2 — strong, moderate effort

### 4. Local AI via transformers.js (privacy-safe, policy-compatible)
- **Use cases, best→first:** (a) **smart-redaction suggestions** — a local NER model flags PII (names,
  emails, IBANs, phone numbers) for one-click redaction; (b) **document layout/region detection** to
  sharpen DOCX fidelity + table detection (feeds Tier-2 #5); (c) **local summarize / ask-the-doc** via a
  small in-browser LLM. All 100% local → GRDF-policy-safe.
- **Mechanism:** `@huggingface/transformers`, ONNX via WASM/WebGPU; lazy-load model (gated behind a user
  action, like OCR assets). Regex+dictionary covers IBAN/email cheaply without a model — start there.
- **ROI:** high for (a) (huge in a regulated doc context) but heaviest (model MBs, WebGPU detect, latency).
- **Spike:** measure a small NER model's download size + per-page latency on WASM vs WebGPU before
  committing; ship the regex/dictionary PII detector first (no model) as the MVP. Effort M-L.

### 5. Table → CSV / XLSX export
- **What:** export detected ruled (lattice) tables to CSV/XLSX. Directly extends the vector-rule extraction
  already built for underline/strike (and the lattice-table ceiling note).
- **Mechanism:** cluster the horizontal+vertical rules into a cell grid → assign words to cells → emit CSV
  (trivial) / XLSX (SheetJS, lazy chunk). **Builds on:** `classifyRuleAsUnderline` path + `reconstructPage`.
- **ROI:** high for data-bearing PDFs; reuses existing extraction. Effort M (pairs with the lattice-table
  ceiling-breaker in `2026-06-15-ceiling-challenge.md`).

### 6. XFDF annotation import / export
- **What:** export the overlay annotation set as XFDF (Acrobat's interchange format) and re-import it — share
  markups without sharing the PDF, round-trip with Acrobat.
- **Mechanism:** XFDF is plain XML; map our element model ↔ XFDF. No new dep. Effort M.

### 7. PDF compare / diff
- **What:** side-by-side visual (pixel) + text diff of two revisions.
- **Mechanism:** render both via pdf.js, pixel-diff (pixelmatch-style on canvas) + text diff on extracted
  flow. Effort M. ROI moderate (revisions/legal).

## Tier 3 — mechanisms (not user features), worth doing for quality

- **Web Worker offloading (comlink):** move export / flowDoc reconstruction / pdf render off the main
  thread (OCR is already worker-based) → keeps the UI responsive on large PDFs. Mechanism, M.
- **OPFS for large-doc persistence:** Origin Private File System is faster/larger than IndexedDB for big
  files; keep IndexedDB fallback. Mechanism, S-M.
- **PAdES-BES / TSA via PKI.js:** from `2026-06-15-ceiling-challenge.md` — pure-JS CAdES signed attributes
  + RFC-3161 timestamp; TSA needs network (privacy trade-off, opt-in). M-L.

## Recommendation (if we pick up new work)
1. **Searchable-PDF OCR layer** — biggest ROI/effort, recognition half already exists.
2. **Sanitize/metadata-scrub** — pure ethos fit, no new deps, S-M.
3. **Local PII detector (regex/dictionary MVP) → optional transformers.js NER** — policy-safe smart redaction.
4. **File System Access API** — low-effort desktop UX win (feature-detected).

All four are 100% client-side and need no server. Each should start with the named **spike** to validate
size/latency/round-trip BEFORE committing to the full feature — per the "research + test before commitment"
directive.

Sources: File System Access API support (developer.chrome.com/docs/capabilities/web-apis/file-system-access;

HF v3 WebGPU blog); PKI.js (github.com/PeculiarVentures/PKI.js).
