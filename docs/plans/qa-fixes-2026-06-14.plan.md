## Stage 1 — ISSUE-3: DOCX/PDF image extraction (commonObjs)  · P1 · highest confidence
- **Root cause (verified):** `exportService.ts:372` calls `page.objs.get(imageName)` only. `g_`-prefixed images live in `page.commonObjs`; `page.objs.get` throws → swallowed by the `:394` try/catch → silent skip. `drawImage(bitmap)` already works for `VideoFrame` (runtime), so the `ImageBitmap` TS type is cosmetic.
- **TDD (write first, must fail):** `*.browser.test.ts` — load a PDF whose image is in `commonObjs` (CV-like / `qa-imagetext.pdf`), export DOCX, unzip, assert `word/media/` non-empty + valid image header. Confirm it FAILS on current code.
- **Fix:** at `:372`, resolve the image via `page.commonObjs.has(imageName) ? page.commonObjs.get(imageName) : page.objs.get(imageName)` (guard each `.get` since unresolved objs throw). Widen the TS type to `{ width; height; bitmap?: CanvasImageSource }`. Keep the existing pre-render that populates objs.
- **Acceptance:** `qa-imagetext.pdf` → DOCX has ≥1 media file; CV (if available) 4/4; re-check `AttestationDeDroits` 8→ (expect ≥3, ideally 8). Existing jsdom suite stays green.
- **Verify:** browser test green; manual DOCX open shows the image.

## Stage 2 — ISSUE-4: silent no-op on text-less PDF · P2 (partly depends on Stage 1)
- **Root cause (to confirm at exec):** empty flow model → DOCX/MD export path early-returns with no download/feedback. Trace the caller of `flowDocToDocxBlob` (exportService) for the empty guard.
- **TDD:** browser test — export DOCX from `tests/fixtures/qa-imageonly.pdf`; assert EITHER a file is produced (images-only, post-Stage-1) OR a visible toast appears. Must fail now (no blob, no toast).
- **Fix:** when flow has no paragraphs: (a) if images exist (Stage 1), still emit a DOCX containing them; (b) else show a toast (`t('toast.noExtractableText')` — add key to en/fr/ar, locale-sync hook enforces parity). Never silent.
- **Acceptance:** image-only PDF yields a file or a message; locale files key-identical.

## Stage 3 — ISSUE-1: activate toolbar DnD · P1 (smaller than thought — already implemented)
- **Root cause (verified):** `ToolbarCustomizer` (SortableJS) fully implemented but no Sortable instances exist at runtime → `enable()` is never effectively called. Investigate `uiController.ts`/`pdfTurboApp.ts` wiring at exec.
- **Decision:** set SortableJS `forceFallback: true` (pointer-based, not native HTML5 DnD) — both more reliable across browsers AND automatable (Playwright can't drive native DnD; this is why THUMB-DND and the current toolbar can't be auto-tested otherwise).
- **TDD:** browser test — drag a toolbar group/button past another, assert DOM order changed and **persists across reload** (localStorage). Fails now.
- **Fix:** ensure `customizer.enable()` runs after toolbar render; add `forceFallback:true`; confirm `reset()` is wired to the existing Settings button; verify persistence key written.
- **Acceptance:** reorder persists across reload; reset restores default; jsdom suite green.

## Stage 4 — ISSUE-2: heading/styled-font true-edit data loss · P1 (hardest)
- **Root cause (verified):** `replaceShowOpInPlace` (`contentStreamEditor.ts:466`) only rewrites pure-ASCII literal strings; heading CID/TrueType subset fonts are hex-encoded → op gets blanked (delete) but the new text is not re-encoded in that font → lost.
- **TDD:** browser test — edit a heading, export PDF; assert the new string is BOTH text-extractable AND renders ink (pixel band > threshold) at the location. Fails now (0 ink, no text — pixel-confirmed in findings).
- **Fix options (pick at exec, simplest viable first):**
  1. When the original op is hex/CID and can't be re-encoded, **write a new text-show op using a bundled standard font** (e.g. embed Helvetica/NotoSans via pdf-lib) at the matched transform, instead of blank-only.
  2. If (1) is too invasive, **refuse the edit gracefully**: don't delete the original; show a toast "this text can't be edited in place (embedded font)". Prevents data loss even without full re-encode.
- **Acceptance:** heading edit either renders+extracts the new text, OR leaves the original intact with a clear message. No silent deletion. Body-text edits unaffected (regression-guard with a body-text edit test).

## Stage 5 — ISSUE-5: "Add Text" = unified text mode · P2 (decided)
- **Agreed behavior:** one text mode. Click on existing PDF text → true-edit (existing path). Click on an
  empty canvas area → create a new editable text box at the click point.
- **Root cause:** the "Add Text" button currently routes to edit-text mode whose blank-canvas click is a no-op.
- **TDD (two browser tests):** (1) text mode + click existing word → true-edit input appears; (2) text mode +
  click blank canvas → a new editable text element is created. (2) fails now.
- **Fix:** in the text-tool click router (`canvasClickRouter.ts` / `textEditHandler.ts` / `toolModeManager.ts`):
  when in text mode and the click does NOT hit existing text (no `findTextOpAt` match and no text-layer hit),
  create a new empty `TextElement` at the click point and focus it. Keep the button label "Add Text".
- **Acceptance:** both behaviors work from the one button; jsdom suite green.
